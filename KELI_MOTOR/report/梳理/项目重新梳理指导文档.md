# 项目重新梳理指导文档

> 目标：不是马上重写完整代码，而是把现在已经完成的项目拆清楚。  
> 最后你要能做到：知道每个模块为什么存在、怎么接线、CubeMX 里要开哪些外设、代码从哪里搬、每一步怎么验证。

---

## 0. 先定规则

重新做项目时，最容易犯的错误是：一次把旧代码全部搬过去。

这样做的问题是：如果新工程不能跑，你不知道是时钟错、GPIO 错、SPI 错、Flash 错、PID 错，还是电机接线错。

所以我们采用一个原则：

```text
每一步只增加一个新东西。
```

比如先让 LED 闪，再加串口，再加 Flash。  
这样如果某一步坏了，基本就知道是刚刚新增的那一块出问题。

---

## 1. 先给旧项目做“地图”

### 1.1 你要看的文件

先不要看所有代码，只看这些：

| 类型 | 文件 | 作用 |
|---|---|---|
| 主流程 | `MOTOR_TEST/Core/Src/main.c` | 看程序启动后按什么顺序运行 |
| 中断 | `MOTOR_TEST/Core/Src/stm32f4xx_it.c` | 看定时器中断/控制环在哪里 |
| 串口 | `MOTOR_TEST/MDK-ARM/Src/uart.c` | 调试输出 |
| SPI | `MOTOR_TEST/MDK-ARM/Src/spi_Reg.c` | SPI1 Flash、SPI2 FPGA |
| Flash | `MOTOR_TEST/MDK-ARM/Src/w25q64.c` | 外部 Flash 读写 |
| ADC | `MOTOR_TEST/MDK-ARM/Src/adc_reg.c` | 电位器、电流采样 |
| 编码器 | `MOTOR_TEST/MDK-ARM/Src/encoder_reg.c` | 电机测速 |
| PID | `MOTOR_TEST/MDK-ARM/Src/pid.c` | 控制算法 |
| OLED | `MOTOR_TEST/MDK-ARM/Src/OLED_SSD1306.c` | 显示 |

### 1.2 你要写出来的第一张表

新建一个笔记，标题叫：

```text
KELI_MOTOR 模块地图
```

然后写这张表：

| 模块 | 它解决什么问题 | 用到什么外设/引脚 | 对应代码 |
|---|---|---|---|
| LED/基础运行 | 证明程序能跑 | GPIO | CubeMX 生成 + main.c |
| 串口 | 让 MCU 能把信息打印出来 | USART2 PA2/PA3 | uart.c |
| 外部 Flash | 掉电保存 PID 参数 | SPI1 + W25Q64 | w25q64.c |
| 电位器 | 给目标速度 | ADC1_IN0 PA0 | adc_reg.c |
| 电流采样 | 读取电机电流 | ADC1_IN1 PA1 | adc_reg.c |
| 编码器 | 读取实际转速 | TIM3 CH1/CH2 | encoder_reg.c |
| PWM 输出 | 控制电机功率 | STM32 SPI2 发给 FPGA，FPGA 输出 PWM | spi_Reg.c + FPGA VHDL |
| PID | 自动调节电机 | 纯软件 | pid.c |
| OLED/按键 | 显示和修改参数 | I2C/GPIO | OLED_SSD1306.c |

这一步的目的不是写代码，而是知道“项目由哪些零件组成”。

## 2. 把硬件接线先固定下来

### 为什么先整理硬件

代码是根据硬件写的。  
如果你不知道 PA0 接了什么、SPI1 接了什么，CubeMX 里就不知道该开什么外设。

### 你要整理的表

参考 `MOTOR_TEST/硬件接线与调试记录.md`，整理成下面这种格式：

| 功能 | STM32 引脚 | 连接到 | 备注 |
|---|---|---|---|
| USART2_TX | PA2 | CH340 RXD | 串口打印 |
| USART2_RX | PA3 | CH340 TXD | 串口接收 |
| ADC 电位器 | PA0 | 电位器中间脚 | 目标速度 |
| ADC 电流 | PA1 | INA240 OUT | 实际电流 |
| SPI2_CS | PB12 | FPGA CS | STM32 到 FPGA |
| SPI2_SCK | PB13 | FPGA SCK | STM32 到 FPGA |
| SPI2_MISO | PB14 | FPGA MISO | 当前项目基本不用回传 |
| SPI2_MOSI | PB15 | FPGA MOSI | 发送 duty |
| 编码器 A | PC6 | 电机编码器 A | TIM3_CH1 |
| 编码器 B | PC7 | 电机编码器 B | TIM3_CH2 |
| OLED_SCL | 待确认 | OLED SCL | I2C |
| OLED_SDA | 待确认 | OLED SDA | I2C |
| W25Q64_CS | 待确认 | Flash CS | SPI1 |
| W25Q64_SCK | 待确认 | Flash SCK | SPI1 |
| W25Q64_MISO | 待确认 | Flash DO | SPI1 |
| W25Q64_MOSI | 待确认 | Flash DI | SPI1 |

如果某个引脚你不确定，就写“待确认”。不要硬猜。  
“待确认”比错误记录更有价值。

## 3. 新 CubeMX 工程从最小系统开始

### 3.1 新建空白工程

在 CubeMX 中：

```text
New Project
选择 STM32F407 对应型号
Project Manager 里选择 MDK-ARM / Keil
Generate Code
```

### 为什么要从空白工程开始

空白工程就像地基。  
它能把旧项目里混在一起的东西分开，让你重新确认每个模块到底怎么工作。

### 3.2 第一次只配置这些

| CubeMX 项 | 设置 | 为什么 |
|---|---|---|
| SYS Debug | Serial Wire | 保证 ST-Link 能下载和调试 |
| RCC | 按你的板子实际晶振配置 | 时钟是所有外设的基础 |
| GPIO LED | 选择一个板载 LED 引脚 | 用来证明程序已经运行 |
| Clock Tree | 先用稳定配置 | 不追求极限频率，先保证能跑 |

### 验证标准

Keil 编译通过，下载后 LED 能闪。

如果 LED 不闪，先不要继续。  
因为这说明最基础的工程、时钟、下载、GPIO 里面至少有一个没通。

---

## 4. 第二步加串口

### 为什么串口要放前面

串口是 MCU 的“说话方式”。  
后面测试 Flash、ADC、编码器、PID，都需要打印结果。

没有串口，你只能猜。  
有串口，MCU 可以直接告诉你：

```text
Flash ID = 0xEF16
ADC0 = 2048
RPM = 36.5
PID saved
```

### 你要做什么

CubeMX 配置：

| 项 | 设置 |
|---|---|
| USART2 | Asynchronous |
| Baud Rate | 115200 |
| TX | PA2 |
| RX | PA3 |

代码验证：

```c
printf("hello KELI_MOTOR\r\n");
```

### 验证标准

电脑串口助手能看到稳定输出。

如果串口没输出，重点查：

```text
TX/RX 有没有交叉
GND 有没有共地
波特率是不是 115200
打开的是不是 CH340 的 COM 口
```

---

## 5. 第三步加外部 Flash

### 为什么先做 Flash

Flash 和电机没有关系，适合单独测试。  
先让它独立成功，后面保存 PID 参数时就不会混乱。

### 你先不要做 PID 保存

一开始只测试最简单的：

```text
读 ID
擦除一个扇区
写几个字节
读回来比较
断电后再读一次
```

### 为什么先写字节，不写 float

字节最直观。

比如写：

```text
12 34 56 78
```

读回来还是：

```text
12 34 56 78
```

就说明 Flash 基本通了。  
等这个通了，再存 PID 的 `float`。

### 验证标准

串口打印：

```text
W25Q64 ID = 0xEF16
Write PASS
Power off save PASS
```

---

## 6. 第四步加 ADC

### 为什么 ADC 在电机前面

ADC 是输入量。  
你的项目里 ADC 至少有两个作用：

```text
PA0：电位器，给目标速度
PA1：INA240，测实际电流
```

先确认输入读数正确，后面 PID 才有可靠数据。

### 测试顺序

先测 PA0 电位器：

```text
旋钮最小：ADC 接近 0
旋钮中间：ADC 接近 2000
旋钮最大：ADC 接近 4095
```

再测 PA1 电流采样：

```text
电机不转：读数接近零电流校准值
电机转动：读数有变化
```

### 验证标准

串口能打印：

```text
adc_pot = xxx
adc_curr = xxx
```

数值变化方向要符合现实。旋钮越大，目标值越大。

---

## 7. 第五步加 PWM/FPGA 通信

### 为什么 PID 之前要先测试 PWM

PID 是自动调节。  
PWM 是真正控制电机的“油门”。

如果油门本身不通，PID 写得再好也没用。

### 你要先做开环测试

开环的意思是：先不管反馈，只直接给固定 duty。

例如：

```text
duty = 0       电机停
duty = 1000    电机慢转
duty = 2000    电机更快
duty = 4095    接近最大
```

### 验证标准

电机速度能随着 duty 增大而增大。

如果不行，重点查：

```text
SPI2 有没有发出去
FPGA 有没有烧录成功
TB6612 的 STBY 是否拉高
电机电源 VM 是否正常
STM32、FPGA、电机驱动是否共地
```

---

## 8. 第六步加编码器测速

### 为什么编码器要在 PID 前面

PID 需要知道“实际速度”。  
编码器就是速度表。

如果速度表错了，PID 一定会错。

### 你要验证的现象

```text
电机停止：RPM 接近 0
电机慢转：RPM 较小
电机快转：RPM 较大
方向反了：RPM 符号可能相反
```

### 特别注意

如果编码器方向反了，PID 可能会越调越大。  
因为程序以为“速度还不够”，实际却越转越快。

### 验证标准

串口能打印稳定的 RPM，且速度变化符合现实。

---

## 9. 第七步做 PID 闭环

### 为什么现在才做 PID

到这里你已经确认：

```text
PWM 能控制电机
编码器能测速度
ADC 能给目标值
串口能打印状态
```

这时再做 PID，问题就少很多。

### 先做速度单环

不要一开始就做串级 PID。  
先做最简单的：

```text
目标 RPM - 实际 RPM = 误差
PID 根据误差输出 duty
```

确认速度能跟随目标后，再考虑电流内环。

### 再做串级 PID

你的旧项目是：

```text
速度外环：目标 RPM 和实际 RPM 比较，输出目标电流
电流内环：目标电流和实际电流比较，输出 PWM duty
```

这个比单环更复杂，所以要放后面。

### 验证标准

```text
目标速度慢慢变大，实际速度能跟上
没有明显振荡
目标归零时，电机能停
```

---

## 10. 第八步做 PID 参数 Flash 保存

### 为什么最后保存 PID 参数

保存参数是“记忆功能”，不是控制电机的核心功能。

先让 PID 能跑，再保存参数。  
否则你可能会花很多时间调 Flash，但真正的问题其实在 PID 或电机反馈。

### 你需要保留的概念

```c
#define PID_FLASH_ADDR    ...
#define PID_FLASH_MAGIC   ...
```

`ADDR` 表示存到 Flash 哪里。  
`MAGIC` 表示这段 Flash 里的数据是不是有效 PID 参数。

### 推荐结构体

比起 `float buf[8]`，后面更推荐：

```c
typedef struct {
    float magic;
    float speed_kp;
    float speed_ki;
    float speed_kd;
    float current_kp;
    float current_ki;
    float current_kd;
} PID_FlashData;
```

原因是名字清楚，不容易把 `buf[3]`、`buf[4]` 搞混。

### 验证标准

```text
修改 PID 参数
保存到 Flash
断电
重新上电
读回来的参数和保存前一样
```

---

## 11. 第九步加 OLED/按键/菜单

### 为什么放最后

OLED 和按键是人机界面。  
它们让你更方便地看数据、改参数，但不是电机闭环的核心。

核心链路是：

```text
目标输入 -> PID -> PWM -> 电机 -> 编码器/电流反馈
```

这个链路通了以后，再加 OLED/按键才最稳。

### 验证标准

OLED 显示：

```text
目标 RPM
实际 RPM
PWM duty
电流
PID 参数
```

按键能修改参数，并且不会让控制环卡死。

---

## 12. 每个模块都要写“验收记录”

每完成一小步，就写一条记录。

格式固定：

```text
日期：
模块：
我做了什么：
现象：
是否通过：
问题：
下一步：
```

例子：

```text
日期：2026-05-20
模块：USART2
我做了什么：CubeMX 开 USART2，PA2/PA3，115200
现象：串口助手能看到 hello KELI_MOTOR
是否通过：通过
问题：一开始 TX/RX 没交叉，后来修正
下一步：测试 W25Q64 读 ID
```

这样做的好处是：项目不会变成一团记忆。  
以后出问题，你能回头查到“哪一步曾经是好的”。

## 13. 推荐的新工程目录

新 CubeMX 工程生成后，可以慢慢整理成这样：

```text
New_KELI_MOTOR/
  Core/
    Inc/
    Src/
  App/
    app_main.c
    motor_control.c
    motor_control.h
    pid_param.c
    pid_param.h
  BSP/
    bsp_uart.c
    bsp_uart.h
    bsp_flash_w25q64.c
    bsp_flash_w25q64.h
    bsp_encoder.c
    bsp_encoder.h
    bsp_adc.c
    bsp_adc.h
    bsp_fpga_spi.c
    bsp_fpga_spi.h
    bsp_oled.c
    bsp_oled.h
  Docs/
    接线表.md
    调试记录.md
    模块地图.md
```

简单理解：

```text
Core：CubeMX 自动生成的底层
BSP：和具体硬件有关的驱动
App：项目自己的业务逻辑
Docs：你的记录
```

一开始不需要一步到位。  
你可以先按 CubeMX 默认结构做，等功能跑通后再整理。

## 14. 总路线图

按照这个顺序走：

```text
1. 旧项目模块地图
2. 旧项目硬件接线表
3. CubeMX 新建空工程
4. LED 闪烁
5. USART2 串口 printf
6. W25Q64 读 ID / 擦除 / 写入 / 读回
7. ADC 电位器
8. ADC 电流采样
9. SPI2 发 duty 到 FPGA
10. 开环 PWM 控制电机
11. 编码器测速
12. 速度单环 PID
13. 速度环 + 电流环串级 PID
14. PID 参数保存到 Flash
15. OLED/按键/菜单
16. 最终整理代码和文档
```

你每完成一步，都问自己三个问题：

```text
这个模块的作用是什么？
我怎么证明它工作了？
如果它坏了，我优先查哪里？
```

能回答这三个问题，就说明这一步不是“抄过去了”，而是真的掌握了。
