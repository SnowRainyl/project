\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
\markboth{Abstract}{Abstract}

This report presents the design and implementation of a low-speed DC motor control system based on an STM32F407 microcontroller and an AX309 FPGA development board. The system allows the user to set a target speed in the range of 0--100 RPM through a rotary potentiometer. The STM32 reads the target speed, encoder feedback and motor-current signal, runs a cascade PI control algorithm, and sends a 12-bit duty-cycle command to the FPGA through SPI. The FPGA then generates the PWM signal used by the TB6612FNG motor driver.

The project focuses on register-level implementation. On the MCU side, UART is used for debugging output, ADC for potentiometer and current sampling, TIM3 for quadrature encoder measurement, SPI for Flash and FPGA communication, and I2C for OLED display. The control loop also includes a state machine and a target ramp to manage motor start, run and stop transitions. On the FPGA side, the VHDL design includes an SPI slave receiver and a 12-bit PWM generator. The system stores PI parameters in W25Q64 SPI Flash so that tuned parameters can be reloaded after power-on. At the end, Some tests confirm that everything work correctly.
\\

Keywords: cascade PI, STM32F407, FPGA, DC motor control, current sampling, register-level programming, VHDL

\chapter{System Design}


\section{Functional Requirements}

This project implements a closed-loop speed control system for a low-speed DC motor. The user sets the desired speed with a rotary potentiometer, and the microcontroller converts it into a target speed in the range of 0--100 RPM. Encoder feedback provides the measured speed, while the current-sensing circuit provides motor current feedback. Based on these signals, the microcontroller calculates the control output and sends a PWM duty-cycle command to the FPGA through SPI. The FPGA then generates a 12-bit PWM signal for the motor driver.

The system shall provide the following functions:
\begin{itemize}
    \item \textbf{Speed setting and closed-loop control:} support a target speed range of 0--100 RPM and automatically adjust the PWM duty cycle according to encoder and current feedback.
    \item \textbf{Operating status display:} display the target speed, measured speed, PWM duty cycle and motor current on the OLED in real time for direct observation.
    \item \textbf{Debugging output:} speed, current, duty cycle and PI parameters to a PC through UART for runtime monitoring.
    \item \textbf{Non-volatile parameter storage:} store PI parameters in the external W25Q64 SPI Flash. During startup, the microcontroller checks whether valid parameters are available in Flash. If valid data are found, they are loaded.
\end{itemize}
The detailed hardware interfaces, software modules and test results are described in the following chapters.


\section{System Architecture Design}

The overall system architecture is shown in Figure~\ref{fig:architecture}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.95\textwidth]{images/architecture.pdf}
  \caption{System architecture.}
  \label{fig:architecture}
\end{figure}

The system consists of three main parts: the STM32 microcontroller control unit, the FPGA PWM generation unit, and the motor actuation unit. The potentiometer signal is filtered by an RC low-pass circuit and sampled by the MCU ADC as the target speed. The encoder A/B phases are connected to a timer encoder interface for speed measurement. The current-sensing module measures the motor current in the H-bridge output loop, and its output is sampled by another ADC channel.

The STM32 executes the cascade PI control algorithm using the target speed, measured speed and measured current. It then sends a duty-cycle command to the FPGA through SPI2. The FPGA generates the PWM waveform, and the H-bridge driver converts this logic signal into the motor drive voltage and current. The Flash memory, OLED and PC are connected to the MCU through SPI1, I2C and UART, respectively, for parameter storage, status display and serial debugging. The main control path is:

\[
\text{Potentiometer} \xrightarrow{\text{RC + ADC}} \text{STM32 PI}
\xrightarrow{\text{SPI2}} \text{FPGA} \xrightarrow{\text{PWM}}
\text{TB6612} \rightarrow \text{Motor}
\]

Encoder speed and current-sampling signals are fed back to the STM32 to form the closed-loop control system.


\section{Control Strategy}

If only single-loop speed PI is used, the control link can be expressed as:

\[
\text{Target Speed}
\rightarrow \text{Speed PI}
\rightarrow \text{PWM}
\rightarrow \text{Motor}
\]

This structure can regulate speed, but the controller reacts only after the encoder speed has changed. At low speed, the mechanical response is relatively slow, and the motor current may already increase before the speed feedback shows a clear change. Therefore, this project adds a current loop between the speed loop and the PWM output:

\[
\text{Target Speed}
\rightarrow \text{Speed PI}
\rightarrow \text{Target Current}
\rightarrow \text{Current PI}
\rightarrow \text{PWM}
\rightarrow \text{Motor}
\]

In the cascade PI structure, the speed PI compares the target speed with the encoder speed and outputs a target current. The current PI then compares this target current with the measured motor current and generates the PWM duty cycle. In this way, the speed loop determines how much driving current is needed, while the current loop adjusts the PWM output. The target current is limited so that a large speed does not directly produce an excessive PWM command

\section{Input and Feedback}


\subsection{Potentiometer and RC Low-pass Filter}

The rotary potentiometer is connected to PA0 as the target-speed input. Because there may be contact jitter at the sliding end of the potentiometer during mechanical rotation, and because the breadboard supply also contains switching noise from digital circuits, directly connecting the potentiometer to the ADC may cause the sampled value to jump. Therefore, the potentiometer output first passes through an RC low-pass filter, with \(f_c = 1/(2RC)\), to reduce high-frequency noise before entering the ADC.

\subsection{Current Sensing}

This project uses an INA240A2 current-sensing module with an R100 shunt resistor. The R100 resistor in the module is connected in series with the motor, and the connection is

\[
\text{AO1} \rightarrow \text{R100} \rightarrow \text{Motor} \rightarrow \text{AO2}.
\]

Therefore, the motor current flows through R100. The IN+ and IN- inputs of the INA240A2 are connected to the two sides of R100 to measure the voltage difference across the resistor. The INA240A2 therefore senses the shunt voltage without carrying the motor current. The shunt resistance is \(0.1\,\Omega\). The INA240A2 amplifies this differential voltage by 50 and sends the output voltage to STM32. By converting this voltage back into current, the system can obtain the motor current feedback in real time.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.85\textwidth]{images/current_amplifier.pdf}
  \caption{INA240A2 current sensing.}
  \label{fig:ina240}
\end{figure}


The voltage drop on the shunt resistor is proportional to the motor current:
\begin{equation}
V_{\text{shunt}} = I \cdot R_{\text{shunt}}.
\label{eq:shunt_voltage}
\end{equation}

After amplification by the INA240A2, the output voltage is
\begin{equation}
V_{\text{out}} = V_{\text{ref}} + G \cdot V_{\text{shunt}}
= V_{\text{ref}} + G \cdot I \cdot R_{\text{shunt}}.
\label{eq:ina240_out}
\end{equation}

REF1 is connected to GND and REF2 to VCC inside the module, so the nominal zero-current output voltage is \(V_{\text{ref}} = V_{\text{CC}}/2\). The motor current is calculated as:

\begin{equation}
I\,[\text{mA}] = \frac{V_{\text{out}}\,[\text{mV}] - V_{\text{zero}}\,[\text{mV}]}
{50 \times 0.1}
= \frac{V_{\text{out}} - V_{\text{zero}}}{5}
\label{eq:current}
\end{equation}



\subsection{Speed Sensing}

The JGA25-370 motor includes a Hall-effect quadrature encoder with A and B output signals. The encoder is installed on the internal motor shaft, while the controlled speed is measured at the gearbox output shaft. Therefore, the speed calculation must include both the encoder pulses per revolution and the gear reduction ratio. The motor encoder used in this project is 11 PPR, and the gear reduction ratio is 34. TIM3 counts the four edges of the A/B signals, so one output-shaft revolution corresponds to

\[
11 \times 34 \times 4 = 1496
\]

counts. If GPIO external interrupts were used, each edge would trigger a CPU interrupt, and the interrupt load would increase with motor speed. In this project, TIM3 is configured in encoder mode, so the timer hardware completes the A/B quadrature decoding. The program only reads the count difference once per speed update to calculate speed. The timer input filter is also enabled to suppress short pulse interference. The speed is calculated as:

\begin{equation}
\text{RPM} =
\frac{\Delta_{\text{count}}}{N_{\text{count}}}
\cdot \frac{60}{T_s}
\label{eq:rpm}
\end{equation}

Here, \(\Delta_{\text{count}}\) is the encoder count change during one speed-measurement period, \(T_s\) is the speed update period in seconds, and \(N_{\text{count}}\) is the number of encoder counts per output-shaft revolution, including the gear reduction ratio and \(\times 4\) quadrature decoding mode. In this project, \(N_{\text{count}}=11\times34\times4=1496\), and the speed is updated every 10 ms, so \(T_s=0.01\,\text{s}\).

\subsection{PWM Frequency}

The AX309 development board provides an onboard 50 MHz crystal oscillator. The 12-bit PWM counter rolls over after 4096 counts, so:

\begin{equation}
f_{\text{PWM}} = \frac{f_{\text{clk}}}{2^{12}} = \frac{50 \times 10^6}{4096}
\approx 12.207\,\text{kHz}
\label{eq:pwm_freq}
\end{equation}

The PWM frequency is determined by the FPGA clock and the counter length. The 12-bit counter also provides a duty-cycle step of approximately \(100\%/4096 \approx 0.024\%\), which is sufficient for smooth low-speed adjustment in this project.


\section{Motor Drive Circuit}

The FPGA provides only a 3.3 V logic signal and cannot drive the motor directly. The JGA25-370 motor uses a 12 V supply, and its operating current is far higher than the current available from an FPGA I/O pin. Therefore, a TB6612FNG motor driver is inserted between the FPGA and the motor. The FPGA provides the PWM control signal, while the TB6612FNG switches the 12 V motor supply and provides the required drive current.

The PWM signal from the FPGA is connected to the PWMA pin of the TB6612FNG. In this project, AIN1 is connected to 3.3 V and AIN2 is connected to GND, so the driver keeps the motor in one forward direction. The project only controls the speed through PWMA. With this direction setting, a high level on PWMA drives the motor, while a low level disables the drive output. Therefore, the PWM signal repeatedly switches the motor drive on and off. Because the motor winding has inductance, the current changes gradually rather than instantly. The motor can therefore be approximately described by an average voltage:

\[
U_{\text{avg}} \approx D \times 12\,\text{V},
\]

where \(D\) is the PWM duty cycle. The equivalent average voltage for several typical duty cycles is shown in Table~\ref{tab:duty_voltage}.

\section{Power Supply Design and Noise Suppression}

The system uses separate motor and logic supplies, while all modules share a common ground. The STM32F407G-DISC1 and AX309 FPGA development boards are powered by USB from the PC. The TB6612FNG uses two supplies: VM is connected to the external 12 V DC motor supply, and VCC is connected to the 3.3 V logic supply. When the motor starts or the PWM duty cycle changes, the motor current changes and may cause supply fluctuation. Separating the motor supply from the MCU and FPGA logic supplies reduces the influence of these disturbances on digital communication and ADC sampling. A common ground is still required so that PWM, SPI and ADC signals have the same voltage reference.

\subsection{ADC}

The STM32F407 contains three ADC peripheral instances: ADC1, ADC2 and ADC3. This project uses ADC1 to read two analog inputs: PA0 for the potentiometer voltage and PA1 for current feedback. The program selects one channel, starts one conversion, waits until the conversion is complete and then reads the 12-bit result.

The ADC inside the STM32F407 uses a successive-approximation-register (SAR) structure. During sampling, the internal sampling capacitor is connected to the input and stores the input voltage. During conversion, the SAR logic tests the bits from the most significant bit downward. The internal DAC generates the trial voltage, and the comparator determines whether each bit should be kept or cleared. After 12 comparisons, the final 12-bit result is obtained. The basic structure is shown in Figure~\ref{fig:sar}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.85\textwidth]{images/sar.png}
  \caption{SAR ADC structure.}
  \label{fig:sar}
\end{figure}


\[
f_{\text{ADCCLK}}=\frac{84\,\text{MHz}}{4}=21\,\text{MHz},
\]

The corresponding ADC clock period is about \(1/21\,\text{MHz}=47.6\,\text{ns}\). The sampling time is the interval during which the internal sampling capacitor is connected to the input signal. A higher source impedance generally requires a longer sampling time to charge the capacitor accurately. The potentiometer output passes through an RC low-pass filter composed of a 10 k\(\Omega\) resistor and a 100 nF capacitor, so a longer sampling time of 144 cycles is used. The current-sense amplifier has lower output impedance, so 28 cycles are used. The configuration of the two channels is shown in Table~\ref{tab:adc_sampling}.

\[

The filter does not collect all 16 or 8 samples at once, so the actual time window also depends on the update period of each signal.

\subsection{Zero-Speed Handling}

During debugging, the potentiometer ADC reading was still about 9 even when the knob was turned to the minimum. Although this value is small, direct mapping would still create a non-zero speed command near zero. To avoid unintended motion, the program uses a deadband and hysteresis for the potentiometer input.

When the motor is stopped, it starts only if the potentiometer ADC value is greater than or equal to 350. When the motor is running, it stops only if the ADC value falls below or equal to 250. These thresholds are set much higher than the residual zero reading to provide margin against noise and small knob movements near the zero position. The separation between the start and stop thresholds prevents repeated start-stop switching. After the motor is enabled, the valid speed command is mapped to the range from 15 RPM to 100 RPM.


\chapter{Cascade PI Control Algorithm}

This chapter explains the cascade PI control algorithm. The program keeps a general PID calculation function, but \(K_d\) is set to zero in both the speed loop and the current loop. Therefore, this project uses a cascade PI controller. The derivative term is disabled because it can amplify encoder-count fluctuation and current-sampling ripple. This chapter introduces the discrete PI calculation, the cascade structure, the parameter settings and the 1 kHz control loop.


\section{PI Mathematical Model}

The controller calculates its output from the error between the target value and the feedback value. The error is defined as

\[
e(t)=r(t)-y(t),
\]

where \(r(t)\) is the target value, \(y(t)\) is the feedback value, and \(u(t)\) is the controller output. The continuous PID equation is:

\[
u(t) = K_p\,e(t) + K_i\int_0^t e(\tau)\,d\tau + K_d\,\frac{de(t)}{dt}
\]

In this equation, the proportional term responds to the current error, the integral term accumulates past error, and the derivative term responds to error change. The program calculates the controller output every \(T=1\,\text{ms}\). In discrete form, the equation used by the program is:

\begin{equation}
u[n] = K_p\,e[n]
+ K_i \sum_{k=0}^{n} e[k]
+ K_d\,\bigl(e[n] - e[n-1]\bigr)
\label{eq:pid_discrete}
\end{equation}

Here, \(e[n]\) is the current error, \(e[n-1]\) is the previous error, and \(u[n]\) is the current controller output. The coefficients \(K_p\), \(K_i\) and \(K_d\) are the discrete gains tuned directly in the program. Because \(K_d=0\) in both loops, the implemented PI equation is

\begin{equation}
u[n] = K_p\,e[n] + K_i \sum_{k=0}^{n} e[k].
\label{eq:pi_discrete}
\end{equation}

If the output has reached its limit while the accumulated error \(\sum e[k]\) continues to increase, the controller may stay saturated for a long time. To reduce this effect, the program limits the accumulated error to the following range:

\[
-I_{\max}
\leq \sum_{k=0}^{n} e[k]
\leq I_{\max}
\]

The controller output is also limited to the range \([u_{\min},u_{\max}]\). The output range of the speed outer loop is 0--400 mA, and the output range of the current inner loop is 0--4095.

In the implementation, the current error is first added to the accumulated error. The controller output is then calculated. If the output exceeds the allowed range and the current error would push it further into saturation, this newly added error is removed. This avoids a large stored error, which would make the controller slow to reduce its output later.

\section{Startup Control}

\subsection{State Machine}

In the early implementation, a simple motor-enable flag only indicated whether the motor command was active. The same control path was used for startup and normal running. This was not enough because startup needs extra limits: when static friction keeps the motor stopped, the speed-loop accumulated error and the target current can increase before the motor starts moving. If these stored values are carried directly into normal running, the motor may overshoot after startup.

Therefore, the program introduces a startup state machine in \texttt{motor\_fsm.h}. The state machine separates startup, normal running and stopping, so startup-only limits and stopping actions can be applied in the correct phase.

Similar motor-control projects also use state-based logic to separate operating phases, such as ODrive calibration states~\cite{odrive_state} and SimpleFOC PWM phase-state handling~\cite{simplefoc_phase_state}. ODrive also discusses velocity-controller windup and integrator-limit handling~\cite{odrive_integrator}.

The minimum run command is 15 RPM, so the 12 RPM handoff occurs slightly before the normal minimum-speed command is reached.

\subsection{Target Ramp}

The target ramp is applied after the minimum-speed clamp. Even when the potentiometer command is valid, the motor may remain stopped for a short time because of static friction. If the target value rises too quickly during this period, the speed-loop error and current command can build up before the motor starts moving. Therefore, the value sent to the speed PI controller changes only by a fixed step at each speed-loop update. With a speed-loop update rate of 100 Hz and a ramp step of 0.1 RPM, the effective target slope is about 10 RPM/s.


\section{Control Loop Implementation}

TIM6 generates an update interrupt every 1 ms. ADC sampling, state-machine update, PI calculation, duty limiting and SPI transmission are completed in this interrupt, so their total execution time must be less than 1 ms. The current inner loop runs every interrupt, while the encoder speed update and speed outer loop run every 10 ms to reduce speed quantization noise. The main execution order is:
\begin{enumerate}
    \item Read the potentiometer and current ADC channels.
    \item Update the encoder speed and speed-loop flag every 10 ms.
    \item Update the motor state machine.
    \item Run the speed loop when due and run the current loop every 1 ms.
    \item Limit the duty command and send the two-byte value to the FPGA through SPI2.
    \item Write one telemetry snapshot for UART and OLED display.
\end{enumerate}

The ADC clock is 21 MHz. The sampling times of the potentiometer and current channels are 144 and 28 ADC clock cycles, respectively, and each 12-bit conversion requires another 12 cycles. Therefore, the two-channel conversion time is

\[
t_{\mathrm{ADC}}
=\frac{144+12}{21\,\mathrm{MHz}}
+\frac{28+12}{21\,\mathrm{MHz}}
\approx 9.33\,\mu\mathrm{s}.
\]

The SPI2 clock is 5.25 MHz. Transmitting two bytes requires 16 SCK cycles:

\[
t_{\mathrm{SPI}}=\frac{16}{5.25\,\mathrm{MHz}}
\approx 3.05\,\mu\mathrm{s}.
\]

The total time of ADC conversion and SPI transmission is about \(12.38\,\mu\text{s}\), which is much shorter than the 1 ms interrupt period.


\chapter{FPGA Development}

The FPGA design contains three VHDL modules. The project is synthesized using Xilinx ISE 14.7, and the target device is the Spartan-6 XC6SLX9-2FTG256.


\section{SPI Slave Receiver}

The SPI slave receiver samples the SPI signals from the STM32 and reconstructs the 12-bit duty-cycle command.


\subsection{Cross-Clock Domain Synchronization}

A simple SPI slave can use SCK directly to drive the shift register and then transfer the received data into the FPGA system clock domain. In this project, SCK is 5.25 MHz, which is lower than the 50 MHz FPGA system clock. Therefore, the design oversamples SCK in the 50 MHz clock domain, so that SPI reception and the following PWM logic remain in the same clock domain. This approach is similar to the FPGA4Fun SPI slave implementation~\cite{fpga4fun}.

The SCK signal is generated by the STM32 and has no fixed phase relationship with the FPGA internal clock. If it is sampled directly, metastability may occur when the sampling instant is close to an SCK transition. The design uses a two-stage synchronizer for SCK and detects the rising edge from the synchronized samples. The first stage receives the asynchronous input, and the second stage samples it again in the next clock cycle, reducing the probability of metastability propagation. The core code is shown below:
\begin{lstlisting}[style=vhdlstyle,caption={SCK synchronizer}]
p_sync : process(clk)
begin
 if rising_edge(clk) then
 sck_d1 <= sck;
 sck_d2 <= sck_d1;
 end if;
end process;
sck_rise <= sck_d1 and (not sck_d2);  -- single-cycle rising-edge pulse
\end{lstlisting}

\subsection{Two-Byte Duty Cycle Reconstruction}

The PWM duty-cycle value is 12 bits, while SPI2 uses 8-bit data frames. Therefore, the STM32 splits the duty-cycle value into two bytes. The lower 4 bits of the first byte store \(d[11:8]\), and the second byte stores \(d[7:0]\). The reconstruction relationship is

\[
d[11:0]=\{\text{Byte0}[3:0],\,\text{Byte1}[7:0]\}.
\]

After CS\_N is pulled low, the FPGA samples one MOSI bit on each detected SCK rising edge and records the number of received bits with bit\_cnt. After the first 8-bit byte is received, the lower 4 bits are stored as the high part of the duty-cycle value. After the second byte is received, the two parts are combined into the 12-bit duty\_out signal. A rising edge on CS\_N indicates the end of one frame, and the module generates duty\_valid for one clock cycle so that the PWM module can update the duty cycle. The core code is shown below:

\begin{lstlisting}[style=vhdlstyle,caption={SPI duty reconstruction}]
if cs_rise = '1' then
 duty_valid <= '1';
 bit_cnt <= 0;
 shift_reg <= (others => '0');

elsif sck_rise = '1' and cs_d1 = '0' then
 shift_reg <= shift_reg(6 downto 0) & mosi_d1;

 if bit_cnt = 7 then
 temp_hi <= shift_reg(2 downto 0) & mosi_d1;
 bit_cnt <= 8;
 elsif bit_cnt = 15 then
 duty_out <= temp_hi & (shift_reg(6 downto 0) & mosi_d1);
 bit_cnt <= 0;
 else
 bit_cnt <= bit_cnt + 1;
 end if;
end if;
\end{lstlisting}

\section{PWM Generator}

A 12-bit free-running counter is compared with the latched duty-cycle register:
\begin{lstlisting}[style=vhdlstyle,caption={PWM comparator}]
Pwm_out <= '1' when (pwm_cnt < duty_reg) else '0';
\end{lstlisting}
The duty\_valid signal ensures that duty\_reg is updated only at the SPI frame boundary, preventing partial-frame data from affecting the PWM output.


\section{Top-Level Integration}

\texttt{top.vhd} connects the SPI receiver and the PWM generator. The SPI receiver outputs the 12-bit duty-cycle value and a data-valid signal. When the PWM module receives the valid signal, it updates the duty-cycle register and generates the PWM output. The FPGA pins for each input and output signal are specified in \texttt{pin.ucf}. The corresponding physical connections are listed in Table~\ref{tab:fpga_pins}.

\chapter{Testing}

This chapter presents the integration tests and closed-loop speed-control results after the STM32F407, FPGA, motor driver, encoder and current-sensing circuit are connected. The tests cover PWM duty-cycle transmission, parameter storage, OLED display, current sensing, no-load steady-state speed accuracy and a 30-to-60 RPM speed-tracking response.


\section{Test Content and Method}

After the STM32F407, AX309 FPGA, motor driver, INA240A2 current-sensing module and encoder are connected, the integrated system is tested. The test evidence is collected in three forms: physical photos record the hardware connection and OLED display, serial-terminal screenshots record parameter storage and serial debugging information, and UART log data are used to evaluate speed, current and PWM changes. The UART log format is:
\begin{lstlisting}[style=cstyle,caption={UART log format}]
time_ ms,target_rpm,measured_rpm,current_ref_mA,current_mA,pwm
\end{lstlisting}
The serial output frequency should be lower than the control-loop frequency. For example, outputting one frame every 10--20 ms avoids excessive UART transmission inside the 1 kHz control loop.

\section{Debugging Problems and Handling}

The main problems encountered during system debugging include Flash write timing, current-sensor zero-offset calibration, encoder speed fluctuation and duty-cycle oscillation during PI tuning. These issues were addressed by adding a delay after Flash write/erase transactions, using a measured zero-current ADC offset, applying moving-average filters, and reducing the current-loop PI gains.

\section{1\,kHz PI Control Loop (\texttt{TIM6\_DAC\_IRQHandler})}


\begin{lstlisting}[style=cstyle,caption={TIM6 control loop}]
void TIM6_DAC_IRQHandler(void)
{
 if (TIM6->SR & TIM_SR_UIF) {
 TIM6->SR &= ~TIM_SR_UIF;

 Encoder_Update();

 uint16_t adc_val = ADC1_Read_Filtered();
 float setpoint_rpm = (adc_val < 50U) ? 0.0f
 : (float)adc_val * (MOTOR_MAX_RPM / 4095.0f);

 float current_setpoint = PID_Calc(&speed_pid,
 setpoint_rpm, g_encoder_rpm);

 float measured_current = ADC1_ReadCurrent_Filtered_mA();

 float duty_f = PID_Calc(&current_pid,
 current_setpoint, measured_current);
 uint16_t duty = (uint16_t)duty_f;

 uint8_t hi = (duty >> 8U) & 0x0FU;
 uint8_t lo = duty & 0xFFU;
 FPGA_CS_LOW();
 SPI2_ReadWriteByte(hi);
 SPI2_ReadWriteByte(lo);
 FPGA_CS_HIGH();

 g_pid_duty = duty;
 }
}
\end{lstlisting}

\section{Positional-Form PID Implementation}


\begin{lstlisting}[style=cstyle,caption={PID_Calc function}]
float PID_Calc(PID_TypeDef *pid, float setpoint, float feedback)
{
 float err = setpoint - feedback;

 pid->integral += err;
 if (pid->integral > pid->integral_max)
 pid->integral = pid->integral_max;
 else if (pid->integral < -pid->integral_max)
 pid->integral = -pid->integral_max;

 float deriv = pid->kd * (err - pid->err_prev);
 pid->err_prev = err;

 float output = pid->kp * err + pid->ki * pid->integral + deriv;

 if (output > pid->out_max) {
 output = pid->out_max;
 if (err > 0.0f) pid->integral -= err;
 } else if (output < pid->out_min) {
 output = pid->out_min;
 if (err < 0.0f) pid->integral -= err;
 }
 return output;
}
\end{lstlisting}
