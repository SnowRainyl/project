> 上层调用：`MOTOR_TEST/Core/Src/main.c`（`PID_SaveToFlash` / `PID_LoadFromFlash`）

---

## 6.1 为什么要存 Flash，不存会怎样

**一句话：PID 参数整定好之后，每次断电都得重新调，加 Flash 是为了让参数跨电源周期存活。**

断电之后 STM32 的 RAM 会丢数据，整定好的 `kp/ki/kd` 就没了。

Flash 掉电不丢数据，所以可以把调好的 PID 参数存进去，下次上电自动加载。

```
不存 Flash：整定好 kp=1.5 → 断电 → RAM清零 → 上电用默认值 → 重新调参
存 Flash：  整定好 kp=1.5 → save → 断电 → 上电自动加载 → 直接可用
```

### 和老师 memory 课的对应

老师课里最重要的分类是：

```
SRAM = 运行时数据，快，但掉电丢
Flash = 非易失存储，慢，但掉电保留
```

本项目正好对应这几个层级：

| 存储 | 本项目里放什么 | 断电后 |
|------|---------------|--------|
| STM32 SRAM | PID 当前状态、积分项、UART 缓冲、`pid_flash_buf[8]` | 丢失 |
| STM32 内部 Flash | 程序代码、字符串、OLED 字库 | 保留 |
| 外部 W25Q64 SPI Flash | 整定后的 PID 参数 | 保留 |

所以 `pid_flash_buf[8]` 只是 RAM 里的临时缓冲区，真正要长期保存，必须通过 SPI 写进 W25Q64。

## 6.2 W25Q64 写入规则与存储结构

**一句话：Flash 擦除后全是 1，写入只能把 1 改成 0，不能直接把 0 改回 1。**

所以 Flash 和 RAM 最大的不同是：

```
RAM：想写 0 就写 0，想写 1 就写 1
Flash：写只能 1 -> 0；想从 0 变回 1，必须先擦除
```

擦除的结果是：

```
全 0xFF
```

因为 `0xFF = 11111111`。

所以写参数前必须先擦：

```
先擦成全 1
再把需要为 0 的 bit 写成 0
```

热电子注入、F-N 隧穿是底层物理原理，面试时除非被追问，不需要展开。抓住上面这个操作规则就够了。

### 容量层次

```
总容量：64Mbit = 8MB
├── 128 个块（Block），每块 64KB
│   └── 每块 16 个扇区（Sector），每扇区 4KB
│       └── 每扇区 16 页（Page），每页 256B
```

| 操作 | 最小单位 | 最长耗时 |
|------|---------|---------|
| 写（Page Program） | 1字节，最大256B/次 | 3ms（典型 0.7ms） |
| 扇区擦除 | 4KB | 400ms（典型 60ms） |
| 读 | 1字节 | 无限制 |

本项目只存 8 个 `float`：

```
8 × 4B = 32B
```

虽然只写 32B，但擦除最小单位是 4KB，所以保存前会擦掉整个 4KB 扇区。

### 不是 memory-mapped 访问

老师课里区分了 memory-mapped I/O 和外部 SPI Flash。

这个是 STM32 内部 SPI 外设寄存器：

```c
SPI1->DR
```

它属于 memory-mapped I/O，CPU 可以用普通 load/store 访问它。

但 W25Q64 里面的地址不是 STM32 地址空间的一部分：

```text
W25Q64 地址 0x000000
```

这只是 Flash 芯片内部的存储地址。CPU 不能这样访问：

```c
*(uint32_t *)0x000000
```

本项目必须通过 SPI 命令访问：

```
发 0x03 + 3 字节地址 -> 读 W25Q64
发 0x02 + 3 字节地址 -> 写 W25Q64
```

## 6.3 SPI1 配置与 CS 信号

**一句话：CS（片选）拉低表示"我现在和你说话"，拉高表示"这次通信结束"。**

### CS 的作用

SPI 总线可以挂多个从机，CS 用来指定当前选中哪一个：

```
CS 拉低 → 对应从机被选中，开始接收数据
CS 拉高 → 从机取消选中，本次通信结束
```

一次完整的 SPI 事务 = CS↓ … 发数据 … CS↑。

这对应老师 interconnections 课里的 SPI 规则：

```
SPI 不靠地址选择设备
SPI 靠 SPISS/CS 选择从机
Master 产生时钟
Slave 在 CS 有效期间收发数据
```

所以 W25Q64 命令里的 3 字节地址不是“设备地址”，而是 Flash 内部存储地址。设备选择靠 PA4 这根 CS 线完成。

本项目 Flash 用 PA4 作为 CS，软件控制：

```c
#define FLASH_CS_LOW()   GPIOA->BSRR = (1U << (4 + 16))   // 拉低，选中
#define FLASH_CS_HIGH()  GPIOA->BSRR = (1U << 4)           // 拉高，取消
```

### SPI1 时钟配置

SPI1 挂在 APB2（84MHz），BR[2:0] = 011 → 分频 16：

```
SPI1_CLK = 84MHz / 16 = 5.25MHz
```

Mode 0：

```
CPOL=0：SCK 空闲为低
CPHA=0：第一个边沿采样
```

W25Q64 支持 Mode 0 和 Mode 3。这里用 5.25MHz，远低于标准读命令 50MHz 上限，调试优先稳定。

## 6.4 完整写操作流程：WE → 擦除 → WE → 写入

**一句话：每次擦除或写入前都要先发 Write Enable；擦完后 WEL 会自动清零，所以写入前要再发一次。**

### Write Enable 的原因

Flash 有硬件写保护：WEL（Write Enable Latch）默认为 0，拒绝一切写/擦操作。必须显式发 `0x06` 指令才能把 WEL 置 1，之后才接受擦除或写入命令。

WEL 的自动行为：
```
发 0x06（Write Enable） → WEL = 1
擦除或写入完成          → WEL = 0（硬件自动清零）
```

所以每次擦、每次写之前，都要重发 Write Enable。

### 完整顺序

```
① Write Enable（0x06）      → WEL = 1
② Sector Erase（0x20）
③ 等待 BUSY = 0              → WEL 自动清 0，擦除完成
④ Write Enable（0x06）      → WEL = 1（必须重发！）
⑤ Page Program（0x02）
⑥ 等待 BUSY = 0              → WEL 自动清 0，写入完成
```

注意这里有两次 `Write Enable`：

```
第一次给擦除用
第二次给写入用
```

擦除和写入是两个独立的内部操作，不能只发一次 `0x06` 想让两个操作都生效。

代码对应（[w25q64.c:100-135](../../MOTOR_TEST/MDK-ARM/Src/w25q64.c)）：

```c
// PID_SaveToFlash 中：
W25Q64_Erase_Sector(PID_FLASH_ADDR);                        // 含 WE + 擦除 + Wait
W25Q64_Write_4Floats(PID_FLASH_ADDR,      &pid_flash_buf[0]); // 含 WE + 写 + Wait
W25Q64_Write_4Floats(PID_FLASH_ADDR + 16, &pid_flash_buf[4]);
```

### BUSY 位轮询

擦除和写入不是瞬间完成的。

命令发完之后，Flash 内部还要自己慢慢擦/写。STM32 要轮询 `BUSY` 位，等 Flash 真的完成：

```c
static void W25Q64_Wait_Busy(void) {
    uint32_t retry = 200000;           // 约覆盖 400ms 最坏情况
    while ((W25Q64_ReadSR1() & 0x01) != 0) {
        if (--retry == 0) break;       // 防止死等
    }
}
```

`BUSY=1` 表示 Flash 还在忙，`BUSY=0` 才能发下一条擦/写命令。

## 6.5 项目坑：tSHSL 时序违反，静默写入失败

**一句话：CS 拉高表示一条命令结束；下一条命令不能马上开始，要给 Flash 一点收尾时间。**

### tSHSL 是什么

`tSHSL` 指的是：

```
CS 从高电平到下一次拉低之间，至少要间隔多久
```

Flash 内部是状态机，`CS↑` 是“一条 SPI 命令结束”的信号。

芯片需要一点时间完成内部收尾，比如锁存命令、切换状态。如果 `CS` 刚拉高又立刻拉低，Flash 可能还没准备好，新命令会被忽略：

```
CS  ─┐         ┌──────┐          ┌─
     └─────────┘      └──────────┘
                 ↑tSHSL↑
                必须 ≥ 100ns
```

这个时间很短，datasheet 里是 ns 级，但裸寄存器 SPI 连续发命令时仍然可能踩到。

### 现象

- `ReadID` 返回正确的 `0xEF16`（SPI 接线和基本通信没问题）
- `save` 执行，串口打印"已保存"
- 断电重启，串口打印"Flash 无有效参数，使用默认值"
- 回读结果全是 `0xFFFFFFFF`——擦除和写入都没有真正执行

### 根因

问题链路是：

```
Write Enable 结束，CS 拉高
   ↓
马上又拉低 CS 发 Erase
   ↓
间隔不够，Erase 被 Flash 忽略
   ↓
后续写入也没有真正发生
   ↓
回读仍然是 0xFFFFFFFF
```

### 修复

在每次 CS↑ 后加 `HAL_Delay(1)`（[w25q64.c:48,52](../../MOTOR_TEST/MDK-ARM/Src/w25q64.c)）：

```c
static void W25Q64_Write_Enable(void) {
    HAL_Delay(1);                          // 上一事务 CS↑ → 本次 CS↓ 间隔
    FLASH_CS_LOW();
    SPI1_ReadWriteByte(W25X_WriteEnable);  // 0x06
    FLASH_CS_HIGH();
    HAL_Delay(1);                          // Write_Enable CS↑ → 下一命令 CS↓ 间隔
}
```

`1ms` 远大于 `100ns`，虽然保守，但对保存 PID 参数这种低频操作完全可以接受。

### 为什么是静默失败

SPI 没有错误回报机制——从机要么执行命令，要么忽略，主机无法从总线上感知到命令被丢弃。唯一的检测手段是**写完立刻回读验证**。

## 6.6 Magic 数：判断 Flash 是否写过

**一句话：Flash 擦除后全是 0xFF；用一个特定魔数作为"有效标志"——读回来是魔数才加载参数，否则用默认值。**

Flash 出厂或擦除后，每个 bit 都是 1，读出来全是 `0xFF`。所以判断逻辑是：

```
读第一个 float：
  == 12345.678f（魔数）→ 之前存过参数，加载
  != 12345.678f        → 没存过，用默认值
```

注意：不是"读到魔数 = 没存过"——**正好相反**，读到魔数说明之前存过。Flash 没写过时读出 `0xFFFFFFFF`，不等于魔数，才走默认值分支。

`12345.678f` 的 IEEE 754 表示是 `0x4640E6B8`，绝对不等于 `0xFFFFFFFF`，不会误判。

这里用 `float` 做魔数不是因为它特殊，而是因为参数本来就是 `float` 数组，放在同一个数组里最方便。

存储布局（[main.c:80-81](../../MOTOR_TEST/Core/Src/main.c)）：

```c
#define PID_FLASH_MAGIC  12345.678f
static float pid_flash_buf[8];
// [0]=magic, [1]=sp_kp, [2]=sp_ki, [3]=sp_kd
// [4]=cp_kp, [5]=cp_ki, [6]=cp_kd, [7]=0.0

// 地址 0x000000：前 4 个 float（16字节）
// 地址 0x000010：后 4 个 float（16字节）
```

### 回读验证

写完立刻读回来，对比魔数，这是发现静默失败的唯一手段：

```c
W25Q64_Read_4Floats(PID_FLASH_ADDR, verify);
if (verify[0] == PID_FLASH_MAGIC) {
    // 验证 OK，打印 sp_kp
} else {
    // 打印：Flash 写入失败，readback = 0xFFFFFFFF
}
```

如果回读不是魔数，就说明“串口打印 save 完成”不代表真的写进去了。

## 6.7 从课程角度看这个实现还能怎么改进

老师 memory 课里提到，保存参数时更工程化的做法是：

```
magic + version + 参数 + checksum
```

本项目现在已经有：

```
magic + 参数 + 回读验证
```

还没有做：

```
version
checksum
双备份区
```

当前项目只是保存 6 个 PID 参数，写入频率很低，所以这个版本够用。

如果要做得更可靠，可以升级成：

```
参数区 A：上一份有效参数
参数区 B：新参数写入位置
写 B 成功并校验后，标记 B 有效
下次再切回 A
```

这样即使写 Flash 过程中突然断电，也更容易保留上一份有效参数。

还有一个重要原则：

```
不要在 1kHz 控制中断里擦写 Flash
```

原因是扇区擦除最坏可能到 `400ms`，会严重阻塞实时控制。本项目是在用户输入 `save` 命令时保存参数，不在 TIM6 控制中断里擦写，这是合理的。

## 6.8 扩展理论：ROM 家族和 W25Q64 的位置

这部分适合写报告，用来说明 W25Q64 在存储器分类里的位置。

老师 memory 课里可以把非易失存储器看成一个家族：

```
非易失存储器（ROM 类）
│
├── Mask ROM
│   工厂制造时内容就固定，不能改
│
├── OTP-ROM
│   One-Time Programmable，只能写一次
│
├── EPROM
│   可编程，但要用紫外线擦除
│
├── EEPROM / E2PROM
│   电可擦除，通常可以按字节擦写
│
└── Flash
    EEPROM 的改进版，擦除粒度变大，容量更高、成本更低
```

本项目用的 W25Q64 属于：

```
Flash -> NOR Flash -> 外部 SPI Flash
```

所以它的特点是：

```
掉电不丢
可以反复擦写
通过 SPI 命令访问
适合保存参数、配置、小量日志
```

这里“ROM”不要死理解成“只能读”。现代语境里：

```
ROM 类 = 掉电保留
RAM 类 = 掉电丢失
```

Flash 虽然属于 ROM 类，但它是可以擦写的。

## 6.9 扩展理论：NOR 和 NAND 的区别

W25Q64 是 NOR Flash，不是 NAND Flash。

两者都属于 Flash，但内部连接方式不同，导致用途不同。

### NOR Flash

```
每个存储单元更接近独立寻址
可以给一个地址直接读出数据
随机读取方便
适合程序代码、小容量参数、配置数据
```

本项目中：

```text
W25Q64_Read_4Floats(addr, pf)
```

本质就是：

```
发 Read 命令 0x03
发 3 字节地址
从这个地址开始连续读数据
```

这就是 NOR Flash 的典型用法。

### NAND Flash

```
存储单元串联成一串
通常按页读取
容量大、成本低
适合 U 盘、SD 卡、SSD
```

NAND 不适合像本项目这样直接用一个小地址读几个参数。它通常需要页缓存、坏块管理、文件系统或 Flash Translation Layer。

简单对比：

| 类型 | 读取方式 | 优点 | 常见用途 |
|------|----------|------|----------|
| NOR Flash | 随机按地址读 | 读方便，适合代码/参数 | MCU 程序、配置参数、SPI Flash |
| NAND Flash | 按页/块管理 | 容量大，成本低 | SD 卡、U 盘、SSD |

所以 W25Q64 用来保存 PID 参数很合适：

```
参数很小
读取要简单
写入频率低
需要断电保留
```

## 6.10 扩展理论：Flash 的读、写、擦物理机制

Flash 的基本存储单元是浮栅晶体管。

可以先用一个简单模型理解：

```
浮栅里有没有电子
        ↓
影响晶体管阈值电压
        ↓
读电路根据阈值判断 0/1
```

### 编程：1 -> 0

写入数据时，Flash 通过高压把电子注入浮栅。

结果：

```
浮栅带负电
晶体管阈值升高
读出为 0
```

这叫热电子注入。

所以编程操作本质是：

```
把 1 写成 0
```

### 擦除：0 -> 1

擦除时，Flash 通过反向高压把浮栅里的电子拉出来。

结果：

```
浮栅电子减少
晶体管阈值降低
读出为 1
```

这叫 F-N 隧穿。

所以擦除操作本质是：

```
把 0 恢复成 1
```

### 读取：检测阈值

读取时不会移动电子，只是检测晶体管在某个读取电压下是否导通。

所以：

```
读操作很快，且不会破坏数据
写操作较慢
擦除更慢
```

对应本项目：

| 操作 | 项目里的命令 | 典型含义 |
|------|-------------|----------|
| 读 | `0x03 Read Data` | 给地址，读出参数 |
| 编程 | `0x02 Page Program` | 把 1 改成 0，写入 32B 参数 |
| 擦除 | `0x20 Sector Erase` | 把 4KB 扇区恢复成全 0xFF |

### 为什么擦写次数有限

编程和擦除都要让电子穿过很薄的绝缘层。

每次穿越都会对绝缘层造成微小损伤。次数多了以后，浮栅保存电荷的能力变差，数据就可能不可靠。

所以 Flash 有擦写寿命限制，常见量级是：

```
约 10 万次擦写
```

本项目只在用户调好参数后手动 `save`，不是每 1ms 保存一次，所以寿命不是问题。
